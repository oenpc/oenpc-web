# OENPC-WEB 开发计划

> 依据：`功能清单.md`（76 条功能/能力项）、`strata-index.md`（§1 十二条硬约束、§4 十五条陷阱）、
> 以及骨架落地后的实测状态。
> **本计划的核心不是排序，而是"为什么是这个顺序"** —— 顺序错了，后面要成倍返工。

---

## 0. 四条排序原则（先看这个）

| # | 原则 | 依据 |
|---|---|---|
| 1 | **不确定性最大的先做** | SSG 预渲染是本项目**唯一没验证过**的技术点，它决定前台整体结构。放在后期发现不成立，代价是整个前台重写 |
| 2 | **横切关注点与第一个写路径同期织入** | 权限校验、审计留痕、多语、UTC —— 只要有一个写路径漏掉，后面就要回头补几十处 |
| 3 | **每条业务线先做端到端可验证的薄片** | 不"后端全写完再写前端"。骨架阶段已验证：一次贯通的薄片能暴露真问题，而分层推进只在最后才暴露集成问题 |
| 4 | **规范跟着代码长** | 每阶段结束：新增的面补条目、新踩的坑加 §4 并给出可执行检查形态。**否则 STRATA 会退化成一份过期文档** |

### 一个必须先纠正的现有偏差

骨架阶段我给"平台能力"（仓储边界、方言层、迁移、信封）打了 ✅，但：

- **P7「驱动可替换」只做了一半** —— `dialect.ts` 收口了 SQL 方言，但仓储签名直接吃 `DatabaseSync`，**接口抽象数为 0**。换 PG 时方言不用改，但每个仓储的签名与装配点都要动。
- **自动化测试数为 0** —— 而我自己的 `AGENTS.md` 写着「一个功能一个回归脚本」。

**这两条是 P0 的全部理由**：它们现在是一小时的工作量，铺开十个域之后是几十处、几百行。

## P0 · 地基修正（**必须先做**）

| 项 | 内容 | 规模 |
|---|---|---|
| 0.1 | **仓储接口抽象**：`ProductRepository` 接口 + `createSqliteProductRepository(db)` 工厂，装配在 `app.ts` 一处完成 | S |
| 0.2 | **测试基线**：`node:test` 单测 + `regression-<功能>.mjs` 端到端，建立 `pnpm test`；把骨架阶段已验证的 6 项行为固化成脚本 | M |
| 0.3 | **SSG spike**：用假数据验证最难组合 —— 多语 URL + 动态产品路由 + 预渲染产出含 `hreflang` 的静态 HTML + 产物能被 nginx 直接托管 | M |

### 为什么 0.1 必须在最前

现在只有 **2 个**仓储函数、1 个域。抽接口是改 2 个签名；
等 12 个域铺开再抽，是改几十个签名 + 所有装配点 + 所有测试。
**这是本计划里唯一一个"成本随时间线性增长"的任务。**

### 为什么 0.2 必须在业务之前

现在的验证全是我一次性跑的（fixture 用完即删）。在此之上继续叠功能，
等于在**没有回归网**的情况下往上盖楼 —— 而 `AGENTS.md` 已经写了规则却无人遵守，
这会让**其余规范一起失去分量**。

### 0.3 要验证的具体问题（不是"跑个 demo"）

1. 多语 URL 前缀（`/<locale>/...`）与预渲染能否共存
2. 动态路由（每个产品一个页面）在构建期如何枚举 —— 需要从 API 拉全部 slug
3. **`hreflang` 互指在静态 HTML 里是否正确产出**（这依赖列表接口返回全部语种 slug，骨架已实现）
4. 构建产物是否零运行时依赖（直接丢给 A 机 nginx）

**验收**：产出的 HTML 里，每种语种的页面都带齐全部语种的 `alternate` 链接。

## P1 · 前台可见（SSG 站点）

> 目标：**产品"看得见"**。这是这个产品的存在形式，也是唯一直接面向收入的部分。

| 项 | 内容 | 激活的约束 | 规模 |
|---|---|---|---|
| 1.1 | **URL 结构定稿**：`/<locale>/products/<slug>`、分类、首页 —— **这是公开契约，改它等于丢 SEO** | — | S |
| 1.2 | i18n 资源体系（`N` 层）+ 前端 API 客户端（**运行时读取基址**，不 build 写死） | `runtime-config` 已在守 | M |
| 1.3 | 页面：首页（区块化）、产品列表、产品详情、分类筛选 | — | L |
| 1.4 | 每语种 slug + `hreflang` 互指 + `sitemap.xml` + `robots.txt` | **`every-public-page-has-url` 转可判定** | M |
| 1.5 | 图片产物与首屏性能（`PERF` 面） | — | M |

### 为什么前台在后台之前

- 读接口**已经完成**（列表/详情/搜索），前台可以立刻开工，用 seed 数据推进
- 它是最大不确定性（SSG）的落点，P0.3 的结论直接喂给它
- 后台是"管道"，前台是"产品价值"；先用假数据把价值做出来，比先铺管道更能暴露需求偏差

### 验收

`pnpm build` 产出静态站；**每语种页面 URL 独立可索引**；
`strata:check` 中 `no-hardcoded-copy` 与 `every-public-page-has-url` 从「无法判定」转为**可判定**

## P2 · 内容能进去（后台最小闭环 —— 横切关注点在此定型）

> 目标：**不再靠直接写库**。此阶段定型的模式会被后面所有域复制，所以顺序不能随便。

| 项 | 内容 | 规模 |
|---|---|---|
| 2.1 | 认证：登录 + JWT + scrypt + **登录限流**（F7.1, F7.5）| M |
| 2.2 | **权限中间件**：权限点 → 路由守卫（F7.2）—— **第一个写路径就带上** | M |
| 2.3 | **审计留痕**：只追加日志表 + 写入点（F14.1）—— **与 2.2 同期，不单独排阶段** | M |
| 2.4 | 媒体：上传 / 服务端类型体积校验 / 压缩缩略图 / 引用计数与删除保护（F10.1–F10.4, P13–P14）| L |
| 2.5 | 产品写路径：CRUD + 分类树 + 上下架排序 + 批量导入导出（F8.1–F8.4）| L |
| 2.6 | admin SPA：登录页 + 产品列表/编辑表单 + 图片上传（Naive UI 与家族一致）| L |
| 2.7 | **内容变更 → 触发前台重建**（手动/定时，F6.5 落地）| S |

### 为什么 2.2 / 2.3 必须与 2.1 同期

- **权限**：先有 5 个写接口再加权限校验，等于把 5 个接口全部返工；而且很容易漏掉一个 —— 漏掉的那个就是越权入口
- **审计**：`append-only-audit` 是硬约束。事后补意味着回到每一个写路径插日志，且**无法补上已经发生的历史**

### 为什么媒体在 2.5 之前

产品必须有图。**没有图的展示站不是展示站。** 若先做产品 CRUD 再做上传，
产品表单要返工一次才能挂上图。

### 2.4 的两个坑（已在索引 §4）

- **nginx 与 Fastify 两侧都要放开上限**，漏 nginx 会先返回 413，看起来像后端 bug（P-05）
- 媒体删除要有**引用计数**，否则删掉仍被产品引用的图片会让前台 404（P-14）

### 验收

**不通库、只经后台**，能录入一个"带图 + 三语"的产品，并让前台静态页更新

## P3 · 转化路径（询盘）

> 目标：**访客除了跳走，有第二条转化路径**。这是外贸站唯一能留住线索的地方。

| 项 | 内容 | 规模 |
|---|---|---|
| 3.1 | 询盘表 + 提交接口 + 反垃圾（蜜罐 + 限流）（F4.1, F4.4）| M |
| 3.2 | 产品级询盘（自动带产品上下文）（F4.2）| S |
| 3.3 | 后台询盘列表与状态流转（F12.1）| M |
| 3.4 | **SSE 实时提醒**（F12.2, P10–P12）| M |
| 3.5 | 出站点击埋点（F3.4）—— 为 P5 报表供数 | S |

### 3.4 的关键约束

**nginx 必须 `proxy_buffering off`**，否则事件被缓冲，症状是"连上了但收不到"，
而前端与后端看起来都正常（P-06）。
且**只做单向推送 → 用 SSE，不引入 WebSocket** —— WS 的跨域放行、连接鉴权、
断线重连、多进程状态不共享等成本会分散在多个面上，与收益不成比例。

## 关键路径与并行机会

```
P0.3(SSG spike) ──► P1.1(URL 定稿) ──► P1.3(页面) ──┐
                                                    ├──► P2.7(重建回路) ──► P3 ──► P6
P0.1(仓储抽象) ──► P0.2(测试基线) ──► P2.1 ─► P2.4 ──┘
```

- **关键路径**：`P0.3 → P1.1 → P1.3 → P2.7`。最长链条之所以跨 P1 与 P2，是因为
  **2.7 的重建回路依赖 P1 的构建产物** —— 没有前台就没有可重建的东西
- **可并行**：P2 的后端（2.1–2.5）与 P1 的前台可以两人并行 ——
  **接口契约已经定稿**（`packages/shared`），这正是契约层先做的价值
- **不可并行**：P3.4 依赖 2.2/2.3 建立的鉴权与审计模式；P5 依赖前面产生的数据

## 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **SSG 方案不成立** | P1 整体结构重写 | P0.3 先验证**最难组合**（多语 + 动态路由 + hreflang），不是跑个 hello world |
| **图片处理引入原生依赖**（sharp）| 安装与部署复杂化，可能触发沙箱限制 | P0 就试装；不可行则降级为"不压缩 + 上传时客户端预压缩"，并接受图片体积 |
| **重建延迟被当成 bug** | 运营者以为保存没生效，反复保存 | P2.7 必须在后台给出明确提示（陷阱 P-08）；本期不做 ISR |
| **权限/审计后期补** | 大量回头改 + 无法补历史 | P2.2/P2.3 与第一个写路径同期 |
| **多语字段漏传语种** | 静默回落到默认语种，前台显示另一种语言 | 骨架已在服务层强制 `locale` 必填；P1 的每个取数路径都要走它（陷阱 P-11）|
| **`utc-storage` / `shared-contract` 等 3 条约束无检查形态** | 只能靠人读，容易失效 | 见下方"规范侧的要求" |

## 规范侧的要求（每个阶段结束时都做）

1. **新增文件 → 补 §2 条目**（同一次提交）。**读代码看不出来的东西才写**，不贴代码
2. **一组同类文件 → 用目录条目**，不必逐个写（`strata/checks/` 就是例子）
3. **踩到新坑 → §4 加一行，并给它一个可执行检查形态**。写不出来 ≙ 它大概率不会生效
4. **改 `constraints.mjs` 单独提交** —— 让"约束引入的时刻"可追溯
5. **阶段结束重跑** `pnpm strata:selftest` / `strata:check` / `strata:measure:index`

### 要重点盯的三条

`utc-storage`、`error-code-not-text`、`shared-contract` 目前**没有可执行形态**，
原因是静态扫描会误报，而"一个开始喊狼来了的约束会被绕过、然后彻底失效"。
对付它们的唯一办法是**在 code review 里当成硬项**，
并在 P2 之后试着给它们补上检查形态（例如 `multi-locale-schema`
可以在表结构稳定后用 DDL 扫描实现）。

### 什么时候该重新评估 STRATA

**在 P1 与 P2 结束时各重跑一次 `κ` 与 `γ`。**

- `κ < 0.3` → 面已退化为点，**只保留判决层**，索引的维护成本不再值得
- `γ` 此时才可能开始有区分力（它是"新增文件带来新面的比例"，
  需要跨多次真实功能提交；现在被两次初始提交主导）
- 若 γ 不降 → 说明每个新文件都在产生新面，锚定没带来收益 —— **如实报告，别粉饰**

## 建议的起步动作

**只做 P0 的三项，做完停下汇报。** 理由是这三项都是"现在做便宜、以后做贵"的类型，
而且 0.3 的结论会直接改 P1 的写法 —— 不值得在它之前投入任何前台代码。
