## 2. 开工前必须先定的两件事

### 2.1 ★ 后台的文案策略 —— 现在是被「意外豁免」的

**实测发现**（不是推测）：

- `no-hardcoded-copy` 的 scope 是 `⟨V|O⟩ × 全部域`，而 `targets` 由**索引条目的坐标**筛出
  （`run-all.mjs` 里 `resolveScope(entries, constraint.scope)`）。
- 我给 `apps/admin/` 写的是**目录条目** `[X·AU·7·SEC,I18N·M]` —— **坐标是 `X`，不是 `V|O`**。
- 于是后台的所有 `.vue` **一条都没进过这条约束的检查范围**。
- 把它的 `.vue` 手动喂给检查器，报出 **22 处硬编码文案**。

**这意味着**：后台界面是被"目录条目只填了一个坐标"这件事顺手豁免的，
**不是有人决定过它不需要多语言**。这正是 STRATA 所说「把约束锚在坐标上」的副作用 ——
锚对了会自动覆盖，锚错了会**静默漏过**。

**两个选项：**

| 选项 | 做法 | 代价 |
|---|---|---|
| **A（推荐）保持豁免，但显式化** | 在索引条目的 `S` 字段写明：后台是**内部单语工具**，`ADMIN_DEFAULT_LOCALE='zh'`，不走 i18n；并写明**代价**：若将来后台需要多语言，这条约束不会保护它 | 零 |
| B 纳入约束 | 给 `apps/admin/**/*.vue` 补 `⟨V|O⟩` 条目 + 建 admin 的 locale 资源，修掉 22 处 | 本就是一个独立工作量（每个文案都要建键、每个视图都要接 `t()`），且**当前没有多语言需求** |

**我的建议是 A**，理由：后台使用者是中文团队（`ADMIN_DEFAULT_LOCALE='zh'` 本来就是有意选的）；
给内部工具做 i18n 会让 UI 工作量翻倍，而换不来任何用户可见的收益。

**但必须写进索引、并且由你确认** —— 因为"意外豁免"和"有意豁免"的区别，
在三个月后有人要给后台加英文界面时会体现出来：前者会让人以为约束已经保护过了。

> **决定后我会做的事**：更新 `apps/admin/` 条目的 `S` 字段，把决定与代价写清楚。

### 2.2 要不要引入 `vue-tsc`

**强烈建议引入**，且放在第一步。理由：

- 现在 `.vue` 里的类型错误只有**构建失败**或**运行时**才暴露。
- 接下来要写 10+ 个组件（表格列定义、表单校验规则、动态输入……），
  这些地方类型最容易错，而 `vue-tsc` 恰好覆盖。
- 不引入的话，本计划里 P1 的 6 项全都退化成"靠肉眼看"。

代价：引入后可能**暴露一批既有错误**，需要先清一遍。这属于"一次性投入换后续每一步可验证"。

## 3. 优先级

排期依据（三条，按重要性）：

1. **先让后续每一步可验证** —— 所以基础设施排在最前，而不是最好做的排最前。
2. **功能不变的重做优先于新增功能** —— 重做不引入新的业务语义，风险低、见效快。
3. **数据模型已存在但 UI 缺失的，优先于需要改后端的** —— 因为不动契约就不用重跑服务端回归。

### P3 本轮明确不做（写出来是为了避免范围蔓延）

| 不做 | 理由 |
|---|---|
| 富文本编辑器 | 当前 `description` 是纯文本；引入富文本要同时解决**存储格式 + 前台渲染 + XSS 过滤**，是一个独立专题 |
| 图片裁剪 / 压缩 / 缩略图 | 需要图像处理库（`sharp` 等原生依赖），与"服务器上 `npm install` 就能跑"冲突；见部署说明的未做清单 |
| 批量操作（批量上下架 / 删除） | 收益低于风险：批量删除的误操作代价很高，而当前产品量级用不上 |
| 数据导入导出 | 没有明确的使用场景 |
| TOTP 两级验证 | 安全增强，但当前后台只在**内网明文 HTTP** 下运行 —— 先把 TLS 做了收益更大 |
| 内容变更自动重建前台 | 需要构建触发机制（webhook/队列），是一个独立的架构专题 |

## 5. 什么会被自动覆盖（STRATA 的锚定效果）

**这是本计划里最省事的部分**：P1 的 6 项**不需要写任何新规则**，
因为它们是"文件变更"而不是"新面"。已经挂在对应面上的约束会自动生效：

| 已有约束 | 对本次工作的作用 |
|---|---|
| `error-code-not-text` | 所有新视图的错误提示必须走错误码 → 文案 |
| `upload-limits-both-sides` | 媒体选择器的上传限制（前端 10MB / 白名单不含 SVG） |
| `same-origin-first` | 后台的接口调用必须走同源 `/api/`（不能出现硬编码的 API 域名）|
| `runtime-config` | 不允许出现硬编码的 API base |
| `no-hardcoded-copy` | **P0.2 决定它是否覆盖后台** |
| `index-integrity` | P1/P2 新增的文件必须有索引条目（否则 `strata:check` 直接 FAIL）|

**P0.3 是唯一需要新增的约束** —— 这本身是"锚定生效"的证据：
如果锚定没生效，P1 的 6 项会各自需要一条规则。

## 6. 验收与诚实条款

### 每批做完要跑的

```bash
pnpm typecheck                                   # P0.1 之后必须覆盖 .vue
pnpm --filter @oenpc-web/admin build
grep -o '/admin/assets/[^"]*' apps/admin/dist/index.html   # 必须仍是 /admin/ 前缀
pnpm test                                        # 服务端回归（P2.4/P2.6 动服务端时必跑）
pnpm strata:check                                # 基线：exit 2，5 通过 / 0 失败 / 8 无法判定
```
**判据**：PASS 数**不得低于 5**，FAIL 必须为 **0**，新增约束后 PASS 应变为 6。

### 我做不到机械验证的部分（**如实列出，不当成通过**）

| 事项 | 为什么判不了 | 替代手段 |
|---|---|---|
| "好看" | 主观 | 无法判定 —— 由你看截图决定 |
| 交互是否顺手（键盘流、焦点管理） | 需要真实浏览器与人工判断 | 无法判定 |
| 无障碍（对比度、屏幕阅读器） | 需要专门的审计工具 | 本轮不做，如实记录 |
| 移动端适配 | 后台是桌面工具，未定义移动端需求 | 本轮不做 |
| 浏览器兼容性 | 没有多浏览器测试环境 | 本轮不做 |
| **后台 UI 没有自动化测试** | 项目没有 E2E 框架（Playwright 等）| ★ 见下 |

### ★ 一个我必须指出的缺口

**后台 UI 没有任何自动化测试，而且本轮也不打算加。** 这意味着：

- 每次改 UI，验证都靠**手动点**。P1.4 那条"specs 不能被清空"的检查尤其重要 ——
  它是数据丢失类问题，而这类问题**页面不会报错**，只有重新打开才发现。
- 如果后续后台功能变多、改动变频繁，**引入 Playwright 做 3~5 条关键路径的 E2E**
  会比继续手工点更划算。这不是本轮的活，但我建议记进 P2 之后的待办。
