# OENPC-WEB 部署说明

> 实际拓扑：**B 机 `172.19.229.191` 跑应用与数据库，A 机 `172.19.3.47` 放静态产物与 nginx。**
> 本轮上线的是**最基础可用**的一组功能：前台展示 + 后台登录 / 产品管理 / 图片上传。
> 尚未实现的部分见文末「本轮没做的」，别把它当成已齐全。

```
        ┌─ A 机 172.19.3.47 ────────────────┐        ┌─ B 机 172.19.229.191 ──────────┐
浏览器 ─►│ nginx                              │        │ node + Fastify                  │
        │  /        前台 SSG（/var/www/.../site）      │  监听 172.19.229.191:3900        │
        │  /admin/  后台 SPA（/var/www/.../admin）     │  SQLite + 媒体文件              │
        │  /api/    ── 反代 ──────────────────────────►│  在 /opt/oenpc-web/server/data  │
        │  /media/  ── 反代 ──────────────────────────►│                                 │
        └────────────────────────────────────┘        └─────────────────────────────────┘
```

**源码与构建都在 B 机上**（A 机只需要 nginx，不需要 Node 工具链）。
构建完成后把静态产物从 B 传到 A。

---

## 0. 前置检查（**先做，否则会白折腾**）

在 **B 机**上：

```bash
node -v            # 必须 >= 22.19.0
pnpm -v            # 没有就 npm i -g pnpm
```

在 **A 机**上：

```bash
nginx -v && systemctl --version
```

> **为什么死守 Node 22.19**：服务端用了**内置的 `node:sqlite`**。
> 换第三方 SQLite 驱动意味着改数据层 + 引入原生编译依赖，
> 与"能直接跑起来"的目标冲突。**不要在低版本 Node 上试。**

---

## 1. B 机：源码、构建、数据目录

```bash
sudo useradd --system --home /opt/oenpc-web --shell /usr/sbin/nologin oenpc-web

# 源码放这里（构建也在这里做）
git clone <仓库地址> /opt/oenpc-web-src
cd /opt/oenpc-web-src

pnpm install
pnpm typecheck
pnpm test            # 47+ 项；失败就别继续
pnpm build           # 只构建 shared + server（前台要等有数据后再构建，见 §5）
```

建运行目录并放置应用文件：

```bash
sudo mkdir -p /opt/oenpc-web/server/data
sudo chown -R oenpc-web:oenpc-web /opt/oenpc-web

# 应用运行所需（注意排除源码与数据）
sudo rsync -a --delete \
  apps/server/dist/ apps/server/node_modules/ apps/server/package.json \
  /opt/oenpc-web/server/ 2>/dev/null || {
    # 若上面因为路径写法失败，用这个等价做法：
    sudo cp -r apps/server/dist /opt/oenpc-web/server/
    sudo cp -r apps/server/node_modules /opt/oenpc-web/server/
    sudo cp apps/server/package.json /opt/oenpc-web/server/
  }
```

> `data/` 是**最重要的目录**：SQLite 库与上传的图片都在里面。
> 它不随代码发布更新，**升级时千万不要删**。

## 2. B 机：配置 `.env`

```bash
sudo cp deploy/env.production.example /opt/oenpc-web/server/.env
sudo chmod 600 /opt/oenpc-web/server/.env
```

该文件已按你的两台机器填好，只需核对这几项：

| 变量 | 值 | 为什么 |
|---|---|---|
| `OENPC_WEB_HOST` | **`172.19.229.191`** | ★ **不能填 `127.0.0.1`** —— A 机是另一台主机，连不上 B 的回环地址。填错时本机 curl 正常、A 机一律 502，而 502 通常被误判成"应用挂了"。也不要用 `0.0.0.0`（会把端口暴露给所有可达网络） |
| `OENPC_WEB_TRUSTED_PROXY` | **`172.19.3.47`** | A 机地址。不配则所有访客都显示为 A 机 IP，且**登录限流退化成"限流全站"** |
| `OENPC_WEB_SITE_URL` | `http://172.19.3.47` | 构建期烧进静态 HTML，见 §5 的说明 |
| `OENPC_WEB_DB_PATH` / `MEDIA_DIR` | `/opt/oenpc-web/server/data/...` | 绝对路径 |

### ⚠ 一个容易忽略的副作用

因为 `OENPC_WEB_HOST` 绑的是具体地址，**回环地址 `127.0.0.1` 上并没有服务**。
所以在 B 机上自检、以及构建前台时，都必须用 `172.19.229.191`：

```bash
curl -s http://172.19.229.191:3900/api/health | head -c 300
```

## 3. B 机：建管理员账号（**没有它进不了后台**）

```bash
cd /opt/oenpc-web-src
sudo -u oenpc-web OENPC_WEB_DB_PATH=/opt/oenpc-web/server/data/oenpc-web.db \
  node scripts/create-admin.mjs admin '<自己设一个强口令>'
```

- 第一个账号自动是**隐式全权**（否则没人能再授权，系统锁死）
- 口令至少 8 位，不能与用户名相同
- 改口令加 `--reset`；**改口令会一并清掉该账号所有有效会话**

> 本项目**不预置默认账号**。`admin/admin123` 那种做法等于给每个忘了改口令的部署
> 留一个公开后门，而"忘了改"是常态。

---

## 4. B 机：装 systemd 并启动

```bash
sudo cp deploy/oenpc-web-server.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now oenpc-web-server
sudo systemctl status oenpc-web-server

sudo journalctl -u oenpc-web-server -f
curl -s http://172.19.229.191:3900/api/health | head -c 300
```

`/api/health` 会回报**数据库实际路径与已应用迁移数** —— 这两个信息能回答
"数据写哪去了""迁移跑没跑"，比一句 `{"status":"ok"}` 有用得多。

**防火墙（B 机）**：只允许 A 机访问 3900，其余一律拒绝。

```bash
sudo ufw allow from 172.19.3.47 to any port 3900 proto tcp
sudo ufw deny 3900/tcp
```

## 5. 构建前台与后台（**顺序不能反**）

前台是 SSG —— **构建期从 API 拉数据**生成静态页面。所以必须：
**先让后端跑起来并录好内容 → 再构建前台**。没有数据就只会产出一个空站点。

在 **B 机**上（源码目录里）：

```bash
cd /opt/oenpc-web-src

# 后台 SPA：不依赖数据，随时可构建
pnpm --filter @oenpc-web/admin build

# 前台 SSG：★ 依赖运行中的 API 与里面的内容
OENPC_WEB_SITE_URL=http://172.19.3.47 \
OENPC_WEB_API_BASE=http://172.19.229.191:3900 \
  pnpm build:web
```

> **注意 `OENPC_WEB_API_BASE` 用的是 `172.19.229.191` 而不是 `127.0.0.1`** —— 原因见 §2 末尾。

### ★ `SITE_URL` 是构建期烧进 HTML 的

`canonical`、`hreflang`、`sitemap.xml` 里的地址全部由它生成。将来绑了域名要：

1. 改 `.env` 的 `OENPC_WEB_SITE_URL`
2. 改 `deploy/nginx.conf` 的 `server_name`
3. **重新构建前台**（`pnpm build:web` 再传一次到 A 机）

**只改前两项而不重建**，页面里的 canonical 与 hreflang 仍指向旧地址，
搜索引擎会把这些页面判为重复内容 —— 而且不会有任何报错。

## 6. 把静态产物传到 A 机

在 B 机上：

```bash
# A 机的静态目录先建好（或先 ssh 过去建）
ssh root@172.19.3.47 'mkdir -p /var/www/oenpc-web/site /var/www/oenpc-web/admin'

# 前台（注意结尾的斜杠：传的是目录**内容**，不是目录本身）
rsync -a --delete apps/web/dist/client/ root@172.19.3.47:/var/www/oenpc-web/site/

# 后台
rsync -a --delete apps/admin/dist/        root@172.19.3.47:/var/www/oenpc-web/admin/
```

没有 rsync 时用 scp：

```bash
scp -r apps/web/dist/client/. root@172.19.3.47:/var/www/oenpc-web/site/
scp -r apps/admin/dist/.       root@172.19.3.47:/var/www/oenpc-web/admin/
```

## 7. A 机：配置 nginx

```bash
sudo cp deploy/nginx.conf /etc/nginx/conf.d/oenpc-web.conf
sudo nginx -t && sudo systemctl reload nginx
```

文件里已填好 B 机地址 `172.19.229.191:3900` 与静态目录。**动手前先读里面的注释**，
尤其是这三条：

1. **`/api/` 与 `/media/` 必须用 `^~` 且写在 `location /` 之前。**
   否则前台回落会把它们吃掉，前端拿到 HTML 而不是 JSON，
   报错是 `Unexpected token '<'`，看起来像前端 bug。
2. **`client_max_body_size 12m` 必须放开。** nginx 默认只有 1m，
   上传会在 nginx 就被 **413** 拦掉、**根本到不了应用**
   （对应硬约束 `upload-limits-both-sides`）。
3. **`/admin/` 必须与 `apps/admin/vite.config.ts` 的 `base: '/admin/'` 一致。**
   不一致时后台资源请求落到前台站点，同样是 `Unexpected token '<'`。

## 8. 首次验证顺序（照着走一遍）

1. B 机：`curl http://172.19.229.191:3900/api/health` → 200，`appliedMigrations` ≥ 2
2. A 机：`curl http://172.19.3.47/api/health` → 200（**这一步验证反代通了**）
3. 浏览器打开 `http://172.19.3.47/admin/` → 能登录
4. 后台「产品 → 新建产品」→ 填 **zh 与 en 两个语种** → 上传一张图 → 勾「上架」→ 保存
5. 回到 B 机**重跑 §5 的 `build:web`，再执行 §6 的 rsync**
6. 打开 `http://172.19.3.47/en/products/<你填的 slug>` → 应看到产品与图片
7. `http://172.19.3.47/sitemap.xml` → 应包含刚建的产品 URL
8. 查看页面源码，`<head>` 里应有 `canonical` 与多条 `hreflang`

> **第 5 步是最容易困惑的地方**：后台保存后前台**不会自动更新**，
> 因为它是静态页面。必须重跑构建。后台编辑页底部有这条提示。
> 这不代表保存失败（对应索引里的陷阱 P-08）。

## 9. 安全提醒（当前是内网 HTTP，请知悉）

现在**没有域名也没有证书，全程是明文 HTTP**。这意味着：

- 管理员口令在 A 机与 B 机之间的 `/api/` 请求里**是明文的**；
- 会话令牌（`Authorization: Bearer`）同样是明文。

**在没有 TLS 之前，只能放在可信内网**，不要映射公网端口。

要上 TLS 时：

1. 有域名后申请证书（或内网自签并让客户端信任）
2. nginx 加 `listen 443 ssl` 与证书路径，80 段改成跳转
3. `.env` 的 `OENPC_WEB_SITE_URL` 改成 `https://<域名>`，**并重新构建前台**（见 §5）

## 10. 备份（**别跳过**）

```bash
#!/bin/bash
# /etc/cron.daily/oenpc-web-backup   （在 B 机上）
set -e
DEST=/var/backups/oenpc-web/$(date +%F)
mkdir -p "$DEST"

# ★ 用 sqlite3 的 .backup，不要直接 cp ——
#   直接复制正在写的库会得到损坏的文件（还有 -wal/-shm 没合并）
sqlite3 /opt/oenpc-web/server/data/oenpc-web.db ".backup '$DEST/oenpc-web.db'"

# ★ 媒体必须与库一起备：库里存的是媒体 id，图片文件在磁盘上。
#   只恢复其中一个会得到一页破图。
tar czf "$DEST/media.tar.gz" -C /opt/oenpc-web/server/data media

find /var/backups/oenpc-web -mtime +30 -delete
```

## 11. 升级

```bash
# B 机
cd /opt/oenpc-web-src
git pull
pnpm install
pnpm test && pnpm build

sudo systemctl stop oenpc-web-server
sudo rsync -a --exclude data --exclude .env \
  apps/server/dist/ apps/server/node_modules/ apps/server/package.json \
  /opt/oenpc-web/server/
sudo systemctl start oenpc-web-server      # 启动时自动跑迁移
```

> **`--exclude data --exclude .env` 是必须的** —— 漏了会把数据库和配置一起覆盖掉。

改了内容或 URL 后，还要重做 §5 构建与 §6 传输。

## 本轮没做的（**别以为已经有**）

| 缺口 | 影响 |
|---|---|
| **图片压缩 / 缩略图** | 原图直出，上限 10MB。外墙站对首屏很敏感，这是已知性能缺口 |
| **图片宽高未解析** | `width`/`height` 恒为 null，前台须用 CSS 固定容器比例，否则加载时布局跳动（拉低搜索排名） |
| **规格参数编辑界面** | 接口与数据模型支持，后台没有 UI（保存时原样保留，不会被清掉） |
| **分类管理** | 表结构在，无界面，产品一律 `categoryId = null` |
| **询盘（RFQ）** | 未实现。访客目前除了点购买链接跳走，**没有第二条转化路径** |
| **首页区块 / 关于我们 / 新闻** | 未实现，前台首页是固定内容 |
| **用户与角色管理界面** | 只能靠 `create-admin.mjs` 建账号、直接改库分配权限 |
| **报表与导出、审计查询界面** | 审计**已在写**（登录、产品增删改、媒体上传删除），但没有查询界面 |
| **TOTP 两级验证** | 未实现 |
| **内容变更自动重建** | 目前必须手动重跑 `build:web` 再传 A 机 |
| **TLS** | 见 §9，当前是明文 HTTP |
| `.vue` 的类型检查 | 只做了模块形状声明，模板与 script 里的类型错误发现不了（需 `vue-tsc`）|

> 功能清单里标 ✅ 的项表示**需求已确认**，**不代表已实现**。以本表为准。
